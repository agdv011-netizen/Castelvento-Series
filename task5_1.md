# Task 5.1: Оптимизация производительности и управление ресурсами

## Цель
Обеспечить стабильный FPS (60 кадров/с) на целевых устройствах (включая мобильные телефоны среднего сегмента) за счет внедрения систем пулинга объектов, LOD (Level of Detail), эффективной загрузки ассетов и профилирования узких мест.

## 1. Система пулинга объектов (Object Pooling)

### 1.1. Проблема
Частое создание (`new`) и уничтожение (`destroy`) объектов в игровом цикле (частицы, пули, всплывающие тексты, NPC в толпе) вызывает нагрузку на Garbage Collector (GC), что приводит к микро-фризам (lag spikes).

### 1.2. Решение: ObjectPool<T>
Файл: `client/utils/ObjectPool.ts`

**Архитектура:**
-   Предварительное создание пула объектов при инициализации сцены.
-   Метод `acquire()`: Возвращает неактивный объект из пула вместо создания нового.
-   Метод `release(obj)`: Деактивирует объект и возвращает его в пул вместо удаления.
-   Динамическое расширение: Если пул пуст, создать несколько новых объектов (с шагом), но не удалять их потом.

**Объекты для пулинга:**
1.  **Частицы (Particles):** Эмоции над головой, пыль от велосипеда, блики на воде.
2.  **Диалоговые бабблы:** Всплывающий текст реплик.
3.  **Интерактивные маркеры:** Подсветка объектов при наведении.
4.  **Враги/NPC:** Для массовых сцен (если будут толпы).

**Пример реализации:**
```typescript
class ObjectPool<T extends { setActive(bool): void; reset(): void }> {
  private pool: T[] = [];
  private active: Set<T> = new Set();
  private factory: () => T;

  constructor(factory: () => T, initialSize: number = 20) {
    this.factory = factory;
    for (let i = 0; i < initialSize; i++) {
      const obj = factory();
      obj.setActive(false);
      this.pool.push(obj);
    }
  }

  acquire(): T {
    if (this.pool.length === 0) {
      // Расширяем пул при нехватке
      const newObj = this.factory();
      newObj.setActive(false);
      this.pool.push(newObj);
    }
    const obj = this.pool.pop()!;
    obj.reset();
    obj.setActive(true);
    this.active.add(obj);
    return obj;
  }

  release(obj: T): void {
    if (this.active.has(obj)) {
      this.active.delete(obj);
      obj.setActive(false);
      this.pool.push(obj);
    }
  }
}
```

## 2. Уровень детализации (LOD - Level of Detail)

### 2.1. Концепция
Автоматическая замена сложной графики на упрощенную в зависимости от расстояния до камеры.

### 2.2. Реализация для 2.5D/3D сцен
-   **Спрайты/Меши:**
    -   `LOD0` (0-10 ед.): Полное разрешение, все анимации, нормал-мапы.
    -   `LOD1` (10-30 ед.): Уменьшенное разрешение текстуры, упрощенная геометрия.
    -   `LOD2` (>30 ед.): Силуэт или плоский спрайт (billboard), без теней.
-   **Логика переключения:** Проверка дистанции каждый кадр (или раз N кадров) с гистерезисом (чтобы избежать мерцания на границах).

### 2.3. Реализация для UI и фонов
-   **Размытие дальнего плана:** Использование CSS `filter: blur()` или шейдеров для фоновых слоев, которые не в фокусе.
-   **Отключение рендеринга:** Полное скрытие (`display: none` или отключение компонента) объектов, вышедших за пределы камеры (Frustum Culling).

## 3. Управление памятью и загрузка ассетов

### 3.1. Ленивая загрузка (Lazy Loading)
-   Загружать ассеты только тогда, когда они нужны для текущей сцены.
-   Предзагрузка (Preloading) следующей сцены во время отображения экрана загрузки или диалога.

### 3.2. Выгрузка ресурсов (Unloading)
-   При переходе между главами принудительно очищать кэш ассетов предыдущей главы.
-   Сохранять в кэше только "общие" ресурсы (главный герой, UI, основные звуки).

### 3.3. Сжатие текстур
-   Использование современных форматов: **WebP** для UI и спрайтов, **AVIF** (если поддержка позволяет).
-   Генерация атласов (Texture Atlases) для уменьшения количества HTTP-запросов и переключений контекста отрисовки.

## 4. Профилирование и мониторинг

### 4.1. Встроенный Profiler UI
Режим отладки (доступен по хоткею `F3` или в настройках разработчика):
-   **FPS Counter:** Текущие кадры в секунду.
-   **Frame Time Graph:** График времени рендеринга кадра (разбивка на Update, Render, GC).
-   **Memory Usage:** Потребление памяти JS Heap и GPU Memory.
-   **Draw Calls:** Количество вызовов отрисовки за кадр.
-   **Active Objects:** Количество активных сущностей в сцене.

### 4.2. Автоматические тесты производительности
-   Скрипт, проигрывающий "стресс-тест" сцену (максимум частиц, максимум NPC) и логирующий просадки FPS ниже 50.

## 5. Оптимизация физического движка (если используется)

-   **Упрощение коллайдеров:** Использование простых форм (Box, Circle) вместо сложных полигональных мешей для расчетов физики.
-   **Слои коллизий (Collision Layers):** Отключение проверки столкновений между объектами, которые не могут сталкиваться (напр., декорации друг с другом).
-   **Sleeping Bodies:** "Усыпление" физических тел, которые не двигаются, чтобы исключить их из расчетов симуляции.

## 7. Критерии приемки (Performance Budget)

-   **FPS:** Не менее 55-60 кадров/с в обычных сценах, не менее 30 кадров/с в самых тяжелых сценах с эффектами.
-   **Память:** Потребление оперативной памяти не более 300-400 МБ (для мобильных браузеров критично).
-   **Загрузка:** Время перехода между сценами не более 2-3 секунд (при наличии прелоадера).
-   **GC Pauses:** Длительность пауз сборщика мусора не более 50-100 мс (отсутствие видимых фризов).

## 8. Пример интеграции пулинга в систему частиц

```typescript
// Вместо создания новой частицы каждый кадр:
// const particle = new Particle(); 

// Используем пул:
const particle = particlePool.acquire();
particle.position.copy(emitterPosition);
particle.velocity.set(randomX, randomY);
particle.life = 1.0;

// В обновлении частицы, когда жизнь кончилась:
if (particle.life <= 0) {
  particlePool.release(particle);
}
```
